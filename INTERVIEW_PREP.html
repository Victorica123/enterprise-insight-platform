视频内容理解平台 — 面试技术总结文档

版本：v1.1 | 项目：video-platform | 技术栈：Spring Boot 3 + Java 17 + JWT + JPA/H2/MySQL + Redis + @Async/RocketMQ + AI（Whisper兼容接口 + LLM兼容接口）

一、项目一句话介绍

这是一个面向视频内容的AI处理平台。用户可以上传视频（支持单文件和分片续传），后台异步提取音频、调用大模型转写为文字、再总结核心内容。面向面试场景，设计重点在于分布式系统设计、弹性架构、容错降级、外部依赖治理。

三、分片上传设计与实现

3.1 为什么需要分片上传？

  • 大文件（如200MB视频）直接上传：网络抖动导致整份重传
  • 浏览器/网关通常有请求体大小限制（如Nginx默认1MB，Spring Boot默认10MB）
  • 分片后支持断点续传和并发上传

3.3 代码核心逻辑

public ChunkInitResponse initUpload(String fileName, long totalSize, String md5, String owner) {
    // 1. MD5秒传去重
    String existing = redis.opsForValue().get("file:md5:" + md5);
    if (existing != null) return new ChunkInitResponse(existing, true, chunkSize);

    // 2. 创建上传会话
    String uploadId = UUID.randomUUID().toString();
    redis.opsForHash().putAll("upload:" + uploadId + ":meta",
        Map.of("fileName", fileName, "totalSize", String.valueOf(totalSize),
               "md5", md5, "owner", owner, "chunkSize", String.valueOf(chunkSize)));
    redis.opsForSet().add("upload:" + uploadId + ":chunks"); // 空集合占位

    // 3. 24小时TTL，防止僵尸数据
    redis.expire("upload:" + uploadId + ":meta", Duration.ofHours(24));
    redis.expire("upload:" + uploadId + ":chunks", Duration.ofHours(24));

    return new ChunkInitResponse(uploadId, false, chunkSize);
}

用途结构Key原因

3.5 面试高频问题

  • Q：如果客户端重复上传同一个分片怎么办？
    A：SADD 自动去重（Set 特性），已存在分片不会重复计数，合并前还会再校验分片数量，保证幂等。
  • Q：如果合并时少了一个分片怎么办？
    A：merge时先用SCARD核对已上传数量与总数量，不匹配返回错误。
  • Q：并发merge怎么办？
    A：使用分布式锁（见第四节），确保同一uploadId只有一个合并线程。

四、分布式锁（Redisson）

4.1 为什么不用synchronized？

  • 微服务多实例部署时，synchronized只锁当前JVM，跨进程无效
  • 合并分片涉及文件IO + Redis操作 + AI调用，可能持续数十秒

4.2 Redisson看门狗机制

public boolean tryLock(String key, long expireSeconds) {
    RLock lock = redissonClient.getLock(key);
    // 这里的 expireSeconds 不是 leaseTime，而是等待锁的最大时间
    return lock.tryLock(expireSeconds, TimeUnit.SECONDS);
}
  • 看门狗续期：业务线程存活期间，Redisson后台线程每10秒续期30秒
  • 防死锁：如果业务线程挂了（没调unlock），30秒后锁自动释放
  • 正确释放：unlock前先检查isHeldByCurrentThread()，防止误删他人锁
面试话术："当前代码使用 Redisson 的无 leaseTime 重载：tryLock(waitTime, TimeUnit.SECONDS)。获取锁成功后没有显式指定固定租约，因此 Redisson 会使用看门狗机制，默认每10秒检查并续期到30秒，直到业务代码主动 unlock。这样可以避免长任务执行过程中锁过期，同时服务异常退出后锁也会在TTL后释放。"

五、工作流异步处理

5.1 为什么异步？

同步的问题：

上传 → 提取音频(5s) → 转写(30s) → 总结(5s) → 返回结果
         └──────── 用户等了40秒 ────────┘

异步的好处：

上传 → 保存文件(1s) → 扔任务到后台(0.005s) → 返回"已提交"
                                                      └────── 用户无感知 ──────┘
后台：提取音频 → 转写 → 总结 → 更新状态

5.2 @Async vs MQ 对比

对比项@AsyncRocketMQ
依赖零额外依赖nameserver + broker
任务持久化❌ 重启丢失✅ 队列持久化
削峰填谷❌ 线程池饱和崩溃✅ 队列缓冲
水平扩展❌ 单机✅ 多消费者并行
适用场景单机验证、面试演示生产环境

5.3 策略模式实现模式切换

// 1. 定义接口
public interface WorkflowPublisher { void publish(String taskId); }

// 2. @Async实现（默认）
@Component
@ConditionalOnProperty(prefix = "app.mq", name = "enabled", havingValue = "false", matchIfMissing = true)
public class LocalWorkflowPublisher implements WorkflowPublisher {
    @Autowired private WorkflowProcessor processor;
    @Override public void publish(String taskId) { processor.processAsync(taskId); }
}

// 3. MQ实现（配置切换）
@Component
@ConditionalOnProperty(prefix = "app.mq", name = "enabled", havingValue = "true")
public class RocketMqWorkflowPublisher implements WorkflowPublisher {
    @Autowired private RocketMQTemplate rocketMQTemplate;
    @Override public void publish(String taskId) {
        rocketMQTemplate.syncSend("video-task", MessageBuilder.withPayload(taskId).build());
    }
}

切换方式：修改 application.yml 中 app.mq.enabled=true/false，Spring Boot自动装配对应实现。

7.2 为什么try-catch不能抛异常？

如果JWT解析抛异常导致Filter中断，请求不会走到后续的Security过滤器，Spring Security的异常处理机制（AuthenticationEntryPoint）不会被触发，客户端收到的是裸500错误，而不是401 Unauthorized。

九、常见面试问题与话术（Q&A）

Q1：为什么选择Redis做分片上传，而不是数据库？

分片上传是临时会话数据（生命周期24小时），天然适合Redis的TTL自动过期。如果用MySQL需要定时任务清理僵尸数据，增加复杂度。Redis的Hash+Set结构查询和更新都是O(1)，性能远高于数据库。

Q2：分片上传中如果客户端传了错误顺序的分片，合并时会不会乱？

不会。合并时按索引顺序（0,1,2,3...）从磁盘读取并顺序写入目标文件。每个分片保存时文件名就是索引号，所以无论客户端上传顺序如何，最终合并都是有序的。如果某个索引缺失，SCARD会检测到数量不对，拒绝合并。

Q3：分布式锁在项目中解决什么问题？

解决并发merge问题。用户可能快速点击两次"合并"按钮，或者网络重试导致两个请求同时到达。没有锁的话，两个线程同时读写同一个临时目录，会导致文件损坏或重复创建任务。Redisson锁保证同一uploadId同一时间只有一个线程执行合并。

Q4：如果看门狗续期时Redis挂了怎么办？

Redisson会抛出RedisTimeoutException，但锁本身有初始TTL（30秒），Redis恢复后锁会自动过期，不会永久死锁。业务代码中我们在finally块里unlock，即使续期失败，也能在TTL到期后由其他线程获取锁。

Q6：JWT和Session有什么区别？为什么选JWT？

对比SessionJWT
存储服务端内存/Redis客户端（Header）
扩展性需要共享Session（Redis/Sticky Session）无状态，天然分布式
性能每次查存储本地验签，O(1)
吊销服务端删除即可需黑名单或等过期
本项目用户量不大、重启频率低，JWT无状态更适合微服务扩展。如果未来需要强制吊销，可以引入Redis黑名单存储失效token。

Q7：ffmpeg音频参数如何确定的？

业务需求决定参数：转写给AI听，不需要高音质。16kHz是FunASR官方推荐采样率（覆盖人声频率范围）；单声道足够；32kbps mp3在1小时音频约14MB，上传速度快、成本低。如果未来需要音乐识别，会提高到44.1kHz立体声。

Q8：如果转写失败了怎么办？

WorkflowProcessor中catch所有异常，设置状态为FAILED，并记录错误信息到task表。前端轮询task状态时看到FAILED，可以提示用户重试。未来可以加入指数退避重试（如1分钟、5分钟、15分钟后自动重试3次）。

Q9：项目的最大瓶颈在哪里？如何优化？

当前瓶颈在AI转写API的串行调用（单文件）。优化方向：
  1. 长音频切分：把1小时音频按10分钟切分，并行调用多个转写请求，再拼接结果
  2. 本地缓存：相同MD5的视频直接返回已有结果，避免重复调用AI
  3. MQ削峰：生产环境切到RocketMQ，控制消费速率，防止AI接口限流
  4. 预签名URL：大文件不走服务器，直传对象存储（OSS/S3）

Q10：如果面试官问"你做了什么优化"，怎么答？

我主要做了三个层面的优化：
  1. 传输层：分片上传+MD5秒传，大文件上传稳定性提升，重复文件零成本
  2. 计算层：ffmpeg音频压缩（mp3/32kbps/16kHz），把200MB视频压到14MB音频，API调用时间从分钟级降到秒级，成本降低约90%
  3. 架构层：异步工作流+状态机，用户上传后立即返回，后台处理不阻塞；@Async/MQ策略模式，开发和生产环境一键切换

十一、如果要真正部署给别人用，优先做这些

优先级方向建议原因
P0密钥安全所有 JWT/AI/数据库密码改为环境变量或服务器 Secret，不在配置文件写明文避免泄露和误提交
P0数据库从 H2 切到 MySQL/PostgreSQL，补充 Flyway/Liquibase 管理表结构H2 内存库重启丢数据，不适合生产
P0文件存储视频文件迁移到 OSS/S3/MinIO，本地只保留临时分片服务器磁盘容易满，扩容和备份困难
P0反向代理Nginx 配 HTTPS、上传大小限制、静态资源缓存、后端转发公网访问必须有 HTTPS 和基本网关能力
P1任务可靠性启用 RocketMQ，增加失败重试、死信队列、手动重跑接口AI/网络失败是常态，任务必须可恢复
P1限流防刷登录、上传、AI处理按用户/IP限流，并限制单用户并发任务数AI 调用有成本，必须防止恶意消耗
P1监控告警接入 Actuator + Prometheus/Grafana，记录任务耗时、失败率、AI错误码上线后要能知道哪里慢、哪里失败
P1任务分页我的视频列表改分页查询，VideoTask 建 owner/createdAt 索引用户视频多了以后避免一次查全表
P2前端体验token 过期自动清理、上传暂停/继续、失败重试按钮降低真实用户使用门槛
P2成本优化长音频切片转写、结果缓存、按时长预估成本控制 AI 成本和大文件处理时延
落地建议：第一版不要追求复杂微服务。更稳的路径是：单台云服务器 + Docker Compose + MySQL + Redis + Nginx + 对象存储。先让真实用户能稳定上传、查看结果、失败可重试，再逐步引入 RocketMQ 和多实例扩容。
