# 求职与学习路线

这份文档只回答三个问题：这个项目如何用于后端求职、如何现场演示、下一步学习什么。当前项目定位见 `PROJECT_KNOWLEDGE.md`，技术证据见 `VERIFICATION_MATRIX.md`。

## 求职定位

适合投递：

- Java 后端开发工程师（实习、校招、初级）；
- 平台后端、内容处理、文件服务方向；
- 需要展示 Redis、消息队列、对象存储和可靠性实践的岗位。

一句话介绍：

> 我实现了一个可本地完整复现的视频内容理解平台，支持普通上传、Redis 分片续传和 MinIO 直传，并用本地异步/RocketMQ、任务状态机、幂等、限额与补偿机制处理耗时 AI 工作流；功能有页面、测试和真实中间件脚本共同验证。

不要把它包装成已经商业上线的 SaaS。没有真实用户和生产数据时，诚实地称为“完整业务原型和工程实验平台”更可信。

## 简历表述

可根据岗位选择 3-4 条，不要全部堆上去：

- 设计三类视频上传链路：普通 multipart、Redis 分片断点续传和 MinIO/S3 预签名直传，支持分片状态、合并锁、MD5 完整性校验、内容去重及完成回调幂等。
- 将 FFmpeg、转写和摘要建模为可追踪异步任务，支持本地线程池/RocketMQ 切换、短事务状态推进、重复消息幂等占位、失败重试和卡住任务补偿。
- 实现 owner 级资源隔离与并发准入：上传、播放令牌、任务、重试和删除均校验归属；使用用户行悲观锁保证并发活动任务不超过配额，超限返回 HTTP 429。
- 建立可复现验证体系：79 个自动化测试不依赖外部中间件，并通过脚本真实验证 Redis、MySQL、RocketMQ、MinIO 全链路和 MQ 开关 A/B。
- 完成本地可视化异步实验，在相同 4 worker 条件下比较 80 个请求：本地异步 HTTP 接收 54、拒绝 26；RocketMQ 接收 80、拒绝 0，证明 MQ 主要改变积压与拒绝语义，而非降低单任务成本。

数字只引用已有证据。不要声称“并发提升 X 倍”“支持万级 QPS”或“生产可用”。

## 5-10 分钟演示顺序

### 1. 完整业务（2 分钟）

1. 登录平台，展示普通上传、分片上传和对象存储直传三种入口。
2. 上传小视频，观察 `QUEUED -> TRANSCRIBING -> SUMMARIZING -> COMPLETED`。
3. 展示转写、摘要、播放、复制/Markdown 导出、失败重试和删除。

### 2. 大文件与 MinIO（2 分钟）

1. 说明分片上传的价值是失败后只重传缺失分片，不保证单文件天然更快。
2. 展示上传中断后的状态查询和续传。
3. 说明 MinIO 预签名 PUT 让文件不经过应用服务器，降低应用带宽和磁盘压力。

### 3. 异步实验室（2-3 分钟）

1. 使用相同请求数、Mock 延时和 worker 数运行本地 `@Async`。
2. 切换 RocketMQ 后再运行，比较 HTTP 接收、拒绝、活动任务和总完成时间。
3. 给出结论：MQ 把应用线程池前的有限等待变成可持久化积压；任务仍要由消费者处理。

### 4. 可靠性与证据（1-2 分钟）

展示 owner 隔离、幂等、429 配额、503 饱和、失败重试、reaper、测试和验证矩阵。公网部署只作为可选扩展一句带过。

完整台词和准备命令见 `DEMO_SCRIPT.md`。

## 面试知识地图

### Redis 与分片上传

- Redis 保存短期上传会话、已上传分片集合和 TTL；数据库适合长期业务事实。
- Redisson 锁保护合并临界区；接口幂等仍需同时设计，分布式锁不能替代业务唯一约束。
- 分片大小取舍：过小增加请求、Redis 元数据和合并开销；过大则失败重传成本高。
- 秒传是内容级复用，必须先完成可靠哈希校验，并按 owner 控制结果和文件访问。

### RocketMQ 与异步

- MQ 的价值是解耦、削峰、可重试、跨进程消费和更明确的积压语义。
- MQ 不让 FFmpeg 或 AI 调用变快。吞吐约等于 `消费者并发 / 平均处理耗时`，还受 CPU、连接池和外部 API 限流约束。
- HTTP “已接收”不等于任务“已完成”；前端需要任务 ID、状态查询和失败反馈。
- 至少一次投递要求消费者幂等，项目通过原子 claim 控制同一内容的处理所有权。

### MySQL 与事务

- 慢 I/O 不放在事务中，状态变更用短事务，减少连接占用和锁时间。
- 悲观锁用于严格的每用户并发配额；热点用户可能形成锁竞争，因此锁范围只覆盖计数和建任务。
- 状态机需要合法转换、失败原因、更新时间和恢复入口，不能只用一个布尔字段。

### MinIO 与对象存储

- 预签名 URL 将文件数据面从应用服务器移走；应用只负责鉴权、签名和完成确认。
- 完成回调不能相信浏览器声称“上传成功”，服务端必须检查对象存在，并绑定 owner、路径和 token purpose。
- 对象存储解决文件承载和扩展性，不加速转写；处理端仍可能需要流式读取或临时下载。

### 高并发常见问题

- 线程池、数据库连接池、MQ 消费并发和外部 API 限额必须联合配置，不能只调大一个参数。
- 无限排队会把拒绝变成长延迟和内存/磁盘风险；系统需要限额、背压、429/503 和积压指标。
- 重试可能造成重试风暴，应使用次数上限、退避、死信/人工处理和幂等。
- 大文件会带来磁盘爆满、临时文件泄漏、连接超时和孤儿对象，需要生命周期清理与容量告警。

### 安全与隔离

- JWT 只证明身份；每个资源接口仍必须做 owner 授权。
- 播放 token 要绑定 taskId、owner、purpose 和有效期，避免换路径复用。
- 文件名不能直接作为可信存储路径；上传大小、类型和摘要必须服务端校验。

## 学习路径

1. **会演示**：独立启动轻量模式，讲清完整业务状态。
2. **会解释**：不看文档说明 Redis、MQ、MinIO 各自解决和不解决的问题。
3. **会验证**：独立运行完整栈脚本和异步 A/B，读懂 HTTP、任务、数据库和日志结果。
4. **会排错**：从请求 ID、HTTP 状态、应用日志、容器状态、数据库记录、Redis key、MQ 积压逐层定位。
5. **会修改**：完成媒体生命周期或上传会话治理，并补测试、页面情景和故障说明。
6. **会权衡**：解释为什么当前保持单体与可选中间件，而没有立即拆微服务或上 Kubernetes。

## 下一项实践

优先做“媒体生命周期清理”，因为它同时覆盖真实用户需求、数据一致性、对象存储、失败恢复和面试讨论。完成标准：

- 页面可触发并看见删除结果；
- 本地文件与 MinIO 对象都有明确规则；
- 重复删除安全，失败可诊断；
- owner 隔离与异常路径有自动化测试；
- `VERIFICATION_MATRIX.md` 和故障卡同步更新。

随后做上传会话过期/孤儿清理，再收敛统一验证入口。只有拥有可控 API 额度时，才增加真实 AI smoke；公网部署不再是必做项。

## 诚实边界

- 当前 79 个测试和本地脚本证明的是代码行为与本地中间件链路，不等于生产 SLA。
- Mock 延时适合公平验证队列语义，不能代表真实 Whisper/LLM 性能。
- A/B 结果受机器、worker、延时和请求模型影响，面试时必须同时说实验条件。
- 生产部署、备份恢复、长期容量、真实成本和安全攻防尚未经过公网实践。
