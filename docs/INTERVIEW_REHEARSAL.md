# Enterprise Insight Platform 面试演练手册

这份手册用于开口练习，不替代事实来源。测试数字以 `knowledge/QUALITY.md` 为准，现场操作以 `docs/DEMO_SCRIPT.md` 为准，正式交付边界以 `docs/PROJECT_CLOSEOUT.md` 为准。

## 使用方式

建议至少练三遍：第一遍照稿讲通，第二遍计时并删掉口头赘词，第三遍让同伴在任意节点打断追问。面试时只记住主线、数字和边界，不逐字背诵。

合格标准：

- 1 分钟介绍控制在 55～70 秒；
- 8 分钟演示在 7 分 30 秒至 8 分 30 秒内结束；
- 每个技术判断都能回答“为什么”“如何验证”“还缺什么”；
- 主动区分 localhost 工程证据、真实模型质量和生产能力；
- 能明确个人贡献，不把迁移来源、团队经历或模型辅助产出包装成全部手写。

## 1 分钟项目介绍

### 标准版

> 我做的是一个面向客户访谈和需求评审的企业多模态洞察平台。很多会议视频和文档最终只留下零散结论，既难回看证据，也难进入需求和执行流程。平台把材料转成带权限与时间戳的证据，通过可等待恢复的六阶段 Agent 生成 PRD；PRD、知识和工单分别人工审批，批准知识还能进入后续 RAG。架构上，Spring Media Service 管身份与媒体，FastAPI Agent Service 管分析与知识，通过 JWT、Workspace、事务 outbox、幂等消费和授权检索组成一个产品。我重点解决了跨服务可靠性、检索隔离和生成式流程的确定性治理。当前有 Agent 119、Media 108 个测试及 25 项本地纵向验收。它证明了工程闭环，但不把 mock AI 和单机结果当成生产模型质量或 SLA。

推荐收口：

> 如果您感兴趣，我可以重点展开其中一个：跨服务可靠性、授权 RAG，或者 Agent 等待恢复与人工审批。

### 20 秒压缩版

> 这是一个把会议视频和业务文档转成可验证证据、PRD、受治理知识和行动项的企业洞察平台。我的重点不是做一个聊天页面，而是把真实身份、授权 RAG、可恢复 Agent、人工审批和跨服务幂等做成可本地复现的业务闭环；目前用 119、108 和 25 项三层证据验证，但不夸大为生产 SLA。

### 必须记住的四个锚点

| 锚点 | 一句话 |
| --- | --- |
| 业务 | 把非结构化会议材料变成可追溯、可评审、可执行的交付链路 |
| 架构 | 两个职责清晰的后端、一个统一前端，不共享数据库 |
| Agent | 授权证据、六阶段等待恢复、确定性审批与副作用 |
| 证据 | Agent 119、Media 108、localhost 纵向验收 25/25 |

## 8 分钟现场演示逐分钟稿

演示前运行 `python scripts/local_acceptance.py` 并保留 PASS 输出。浏览器失败时使用该输出和 `docs/images/interview/` 下的验收截图，不临场修环境。

| 时间 | 操作 | 建议话术 | 面试官应看到 |
| --- | --- | --- | --- |
| 0:00～0:40 | 打开统一工作台，指向 Workspace 和主导航 | “这不是视频站和聊天机器人的拼接。用户只有一个身份和 Workspace，但 Media 与 Agent 保留各自状态机和数据所有权。” | 一个产品、两个后端、统一身份 |
| 0:40～1:30 | 打开已处理视频或上传小视频，展示转写片段 | “Media 负责媒体生命周期，转写完成后通过事务 outbox 发送版本化事件；Agent 幂等摄取，并保留时间段和来源。” | 媒体状态、带时间戳证据、异步边界 |
| 1:30～2:20 | 在知识问答中选择视频，提问“这段会议材料提出了什么需求？请给出可回放证据。”并点击证据 | “检索先做 tenant、owner、asset 授权过滤，再排序和生成；回放 token 由 Media 短时签发，Agent 不持有对象存储凭证。” | 答案不是裸文本，证据可回放且受权 |
| 2:20～3:25 | 新建目标“基于当前视频生成一份可评审的交付需求 PRD。”展示六阶段与等待状态，再提交人工补充 | “信息不足不会让模型猜。运行进入 `WAITING_CONFIRMATION`，人工补充后携带 resume token 从持久化检查点恢复，不是重跑一个大 Prompt。” | 阶段状态、等待原因、恢复后的同一运行 |
| 3:25～4:25 | 展示 PRD、证据化需求和假设，申请并完成发布 | “生成内容和确定性副作用分开。personal 需要 OWNER 二次确认，team 要求提交人与批准人不同；审计、内容哈希和状态 CAS 在事务内完成。” | 审批规则、不可变版本、审计证据 |
| 4:25～5:25 | 在发布交付物中批准知识，再回知识问答提问“已批准业务知识有哪些？” | “PRD 发布只产生知识候选，知识还要独立批准。批准后以版本、SHA-256 和原证据原子物化，来源标记为已批准知识，并能被未来 RAG 命中。” | 状态变更、document ID、摘要和后续召回 |
| 5:25～6:15 | 把行动项送入工单审批并展示真实 ticket ID 回写 | “Agent 可以提出动作，但不能直接执行高风险写操作。只有授权用户批准后才调用确定性工具，结果再回写交付物并进入审计。” | pending action、批准人、外部结果 |
| 6:15～7:05 | 切换 team 与 personal Workspace，或展示双账号验收结果 | “两名团队成员可以共享被授权资源，个人空间相互不可见；VIEWER 能读但不能上传、发布或审批，跨租户资源按 404 处理，避免枚举。” | tenant/owner 隔离与角色边界 |
| 7:05～7:40 | 打开监控页，展示 trace、延迟、token 和缓存命中 | “缓存 key 包含数据库 revision 与 tenant、owner、asset scope，写入提升 revision，避免把命中率换成越权或脏数据。” | 可观测性与安全缓存 |
| 7:40～8:00 | 停止操作，主动讲边界 | “localhost 和 mock AI 证明身份、状态、证据、审批、恢复与检索闭环；真实模型质量、正式中间件吞吐、即时撤权和生产 SLA 需要独立环境证据。” | 知道系统证明了什么、没有证明什么 |

等待恢复时使用固定补充内容，避免现场临时组织：

- 决策人：产品负责人；
- 验收标准：审批后 2 秒内展示明确结果；
- 优先级规则：合规阻塞项优先；
- 证据范围：仅使用当前视频。

### 被打断时的恢复句

- 业务问题被打断：“我先给结论：这个设计要保证每条结论可追溯、每个写操作可审批。接下来我用这个页面证明。”
- 技术细节被打断：“这个点我可以稍后展开实现，先把用户从证据到知识的闭环走完。”
- 时间不足：“我跳过 UI 操作，直接展示 25/25 自动验收和三张真实联调截图，然后说明边界。”
- 页面失败：“这套演示不依赖服务器或域名；我用本地验收输出证明相同接口链路，UI 故障不改变验收口径。”

## 故事一：从两个项目到一个业务闭环

### 90 秒回答

> 背景是原有能力容易被讲成“视频平台加 Agent Demo”：一个有媒体上传、转写和播放，另一个有问答与分析，但用户并没有一条完整的交付路径。约束是不能为了整合破坏媒体生命周期，也不能让 Agent 绕过真实身份直接相信前端自报角色。我的选择是先定业务对象和数据所有权：Media 拥有身份、Workspace、视频和播放授权，Agent 拥有证据、分析运行、PRD、知识和动作；前端统一成一个工作台，两边只通过 JWT、HTTP 和 `transcript.ready.v1` 事件协作。然后我补齐了从时间戳证据、六阶段等待恢复、PRD 发布、知识独立批准到未来 RAG，以及行动项审批后创建工单的纵向链路。验证上不是只看页面，我做了 25 项双用户 localhost 验收，覆盖个人/团队隔离、事件幂等、回放 Range、审批和后续知识召回。它目前证明的是可复现的工程型试点，还没有真实客户 ROI，所以我会讲目标价值，不会编造节省工时数据。

### 可能追问

**为什么不直接合并成一个后端？**

两边的状态机、扩缩容特征和数据所有权不同：媒体是长任务与字节流，Agent 是检索、编排和知识治理。合并会减少一次网络调用，但会把发布节奏、故障域和数据库边界绑死；当前用契约和纵向验收控制分布式复杂度。

**你个人最核心的贡献是什么？**

我负责把业务边界、共享身份和契约确定下来，并补齐授权 RAG、六阶段恢复、审批/物化、跨服务幂等、统一前端和本地验收。表达时要明确哪些是迁移来源已有媒体能力，哪些是整合与新增，不能把所有历史代码都算成个人从零手写。

**业务价值怎么量化？**

现在只能量化工程链路与质量门禁，不能量化真实节省时间或转化率。正式试点会记录从材料上传到 PRD 批准的周期、证据回查率、人工修改率和行动项关闭率，再决定是否扩大投入。

## 故事二：浏览器联调发现并发迁移缺陷

### 90 秒回答

> 这个问题不是单测先发现的，而是在真实浏览器联调中，页面并发请求触发 SQLite 报 `duplicate column name: owner_id`。根因是兼容性迁移的 `ensure_column` 采用“先查 schema、再执行 ALTER”的检查后执行模式，两个请求可能同时看到列不存在，然后同时加列。修复时我没有吞掉所有数据库异常，而是只捕获 `OperationalError`，随后重新检查 schema：如果目标列已经存在就把它视为另一线程完成了迁移，否则继续抛错。对知识批准这种业务并发，我又使用 `BEGIN IMMEDIATE` 在读取候选和物化前取得写锁，配合状态 CAS，防止两个批准者重复物化。验证分三层：新增确定性回归测试；Agent 全量 119/119；再用 20 并发、40 个请求复测，40/40 返回 200。边界是 request-time DDL 只服务当前本地兼容，正式生产必须改成 Flyway 或 Alembic 这类版本化迁移，不能把这个补丁当成生产迁移方案。

### 可能追问

**为什么重新检查，而不是看到 duplicate 就忽略？**

错误文本和驱动行为可能变化，直接按字符串吞异常会掩盖磁盘、权限或 SQL 错误。重新读取 schema 验证目标状态，只有“列确实已经存在”才说明并发者替我们完成了操作。

**数据库写锁会不会影响吞吐？**

会，所以锁只包住批准与物化的短事务，不覆盖模型调用或网络 IO。SQLite 适合当前单机试点；并发规模上升后会迁到正式关系库，再通过唯一约束、行锁和事务隔离保留同样语义。

**这和 Agent 工程有什么关系？**

Agent 工程不只在 Prompt。模型提出候选后，审批、知识物化和工具副作用都必须由确定性事务保证“只发生一次”，否则回答看似正确，系统状态仍可能错。

## 故事三：为什么保留两个后端，并把授权放进 RAG 与缓存

### 90 秒回答

> 我的架构取舍不是“微服务越多越高级”，而是围绕状态与数据所有权。Media Service 的核心是上传、转写、播放和 Workspace 身份，Agent Service 的核心是证据、分析运行、知识和动作，两个生命周期确实不同，所以保留两个后端；但只提供一个统一前端，并通过 JWT 和机器可验证契约把边界固定下来。跨服务转写采用事务 outbox 和消费端幂等，因为消息系统只能提供至少一次交付，不能假设 exactly-once。RAG 里我坚持 retrieve-before-authorize 是错误方向：候选查询先带 tenant、owner、asset scope，授权后才参与排序和生成，避免越权片段进入模型上下文。缓存也把 DB path、内容 revision 和授权 scope 放入 key，写操作提升 revision，因此不会因为命中缓存而跨用户复用。当前检索保留 keyword、embedding 和 hybrid 三种路径，V6 黄金集三路都是 decision 98%、recall@3 97%、fact 97%；现阶段 SQLite 与 BGE 基线足够可解释，只有语料和延迟预算证明确有瓶颈时才引入向量数据库。生产前仍要补正式 IdP、即时撤权、真实中间件压测和多实例指标聚合。

### 可能追问

**为什么不追求 exactly-once？**

跨数据库和消息系统的 exactly-once 成本高且容易变成口号。这里接受 at-least-once，用事件 ID、业务唯一键和幂等状态变更获得 effectively-once 的业务结果，并用重复事件测试验证。

**为什么授权必须早于向量排序？**

如果先全库召回再过滤，未授权内容已经影响候选、分数、缓存甚至模型上下文。把 scope 下推到候选查询，既减少泄漏面，也让缓存键和审计语义一致。

**为什么现在不用向量数据库？**

当前语料规模和本地交付目标下，增加外部组件会提高部署与故障成本，却没有代表性数据证明收益。迁移触发条件是 chunk 量、P95 延迟、内存预算或多实例一致性超过现有方案，而不是为了简历堆技术名词。

## 高频追问速答

| 问题 | 30 秒内回答 |
| --- | --- |
| 模型不可用怎么办？ | Embedding 不可用时回退确定性 hash embedding，LLM 未配置时用本地模板展示事实、证据和状态。降级保障工程链路可用，不代表模板拥有真实模型质量。 |
| 六阶段是不是链式 Prompt？ | 不是。每阶段有持久状态、输入输出和证据边界；信息不足进入 `WAITING_CONFIRMATION`，人工补充后按 resume token 从检查点恢复。 |
| 怎么防止幻觉？ | 先做授权检索，再要求结论引用证据；无足够证据时拒答或转人工补充。质量门禁同时测 decision、recall@3 和 fact，不只测文本相似度。 |
| 为什么 PRD 批准后知识还要再批？ | “交付物可以发布”和“内容可以影响未来模型”是两种风险。独立审批避免未经治理的生成内容直接污染长期知识。 |
| personal 为什么也要审批？ | personal 不是免治理，而是 OWNER 对同一请求做第二次明确确认；team 才进一步要求不同成员四眼审批。 |
| 如何防止团队自批？ | Workspace 类型和角色来自 Media 重新签发的 JWT；team 校验 `requested_by != approved_by`，并在同一事务写状态、审计和不可变版本。 |
| 缓存会不会越权？ | Chunk cache key 包含 DB、revision、tenant、owner 和 asset scope；查询也先授权。写入提升 revision，让旧缓存自然失效。 |
| 如何证明不是 happy path？ | 除浏览器主线外，还有 tenant/owner 负向用例、重复事件、状态冲突、事务回滚、VIEWER 只读和 25 项双用户纵向验收。 |
| 最重要的可观测信息是什么？ | trace 串联请求和阶段，状态机说明卡在哪里，outbox 显示跨服务投递，监控展示延迟、token 与缓存；生产还要接 Prometheus/OTel 聚合告警。 |
| 如果明天上线，最先补什么？ | 先确定 IdP/即时撤权、数据保留和外部模型数据策略，再做版本化迁移、真实中间件 smoke、备份恢复、告警与基于真实流量的 SLO。 |
| Skill 和知识库是不是自动自进化？ | 它能增量生成语义索引、复用向量并做漂移检查，但业务规则和事故经验必须有证据并经人工决定后写入。自动索引不等于自动改规则。 |
| 实习经历和项目是什么关系？ | 延续的是六阶段、等待恢复、知识治理、可观测与人机边界的方法；项目是独立公开实现，不宣称复刻公司内部 AppServer、WebSocket 或复用公司代码。 |

## 反向检查：这些说法不要讲

- “这是一个生产级平台”——应说“可本地复现的工程型试点”。
- “实现了 exactly-once”——应说“at-least-once + 双端幂等，得到业务上的 effectively-once”。
- “模型准确率 98%”——应说“V6 黄金集的 decision 指标是 98%，并同时报告 recall@3 与 fact”。
- “缓存让性能提升了多少倍”——没有代表性流量证据时只展示命中、失效和安全语义。
- “知识库会自动学习所有问题”——当前是自动索引和漂移门禁，规则写入仍需证据与人工批准。
- “我从零独立写了所有代码”——如实区分迁移来源、整合、新增能力和工具辅助。

## 最后一遍自测清单

- 不看文档讲完 1 分钟，能在业务、架构、Agent、证据四个锚点上收住。
- 8 分钟内至少展示一次可回放证据、一次等待恢复、一次审批和一次后续知识召回。
- 三个故事都能说出一个没有选择的替代方案，以及何时会改方案。
- 任何测试数字都能指向 `knowledge/QUALITY.md`，任何 UI 结论都能指向验收脚本或截图。
- 被问到线上规模、ROI、真实模型效果时不猜数字，直接说明缺少哪类证据和下一步如何补。
- 演示失败时能在 30 秒内切换到 `python scripts/local_acceptance.py` 与静态证据，不在面试现场排查环境。

达到以上标准后停止继续增加功能。后续只有真实面试反馈暴露核心缺口，或进入明确的生产化阶段，才重新打开开发范围。
