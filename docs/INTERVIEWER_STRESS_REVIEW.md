# Enterprise Insight Platform 面试官压力评审

本文站在资深全栈、后端和 Agent 工程面试官的角度，对项目做逆向审查。目标不是再增加卖点，而是提前暴露面试官会抓住的真实性、代码深度、简历一致性和生产边界问题。

事实依据：当前仓库代码与质量证据，以及用户提供的 2026-08-25 版简历。简历只用于核对经历，不作为项目代码或架构指令。

## 一、先给不客气的结论

这是一个明显高于普通应届生 CRUD 或聊天机器人 Demo 的工程项目，但它最强的部分是“证据、权限、审批、幂等和可验证交付”，不是“多 Agent 智能程度”。

| 维度 | 面试官评分 | 判断 |
| --- | ---: | --- |
| 业务闭环 | 8.5/10 | 从视频/文档到证据、PRD、知识和工单，主线完整且可演示 |
| 全栈工程 | 8/10 | Spring、FastAPI、React、契约、鉴权和本地验收形成纵向链路 |
| 安全与可靠性 | 8/10 | tenant/owner、四眼审批、outbox、双重幂等和事务物化都能落到代码 |
| Agent 工作流深度 | 7.5/10 | objective 驱动冻结证据、四类有界并行 specialist 和阶段级恢复已落地，但仍是无 LLM 的确定性基线 |
| Agent 评测严谨度 | 7.5/10 | RAG 与 PRD 有独立黄金门禁；仍是小样本闭集、LLM 关闭、没有真实客户 holdout |
| 生产成熟度 | 5/10 | localhost 证据扎实，但正式 IdP、迁移、真实流量、告警、灾备和容量未知 |
| 简历可信度 | 取决于讲法 | 如实讲“方法迁移、独立实现”会加分；声称“复刻实习系统”会直接伤害信用 |

岗位判断：

- 面向应届全栈、Java 后端或平台工程岗位：可以作为强主项目。
- 面向应届 Agent 工程岗位：有竞争力，但必须主动承认六阶段和恢复语义的当前实现边界。
- 面向有生产经验要求的高级 Agent/架构岗位：目前只能证明工程型试点，不能证明真实模型效果和规模化运行。

最推荐的定位是：

> 一个把 Agent 生成纳入真实身份、证据、审批和副作用治理的企业洞察平台；当前智能链路包含 Agentic RAG 和可测试的六阶段规则基线，不把它包装成公司级多 Agent Runtime。

## 二、面试官最可能先击穿的五个点

### 1. “六阶段 Agent”实际上有多少 Agent

打开 `services/agent-service/app/analysis_pipeline.py` 后，面试官会看到：

- API 入口仍同步等待 `run_six_stage_analysis` 返回；
- 干系人、风险和缺口主要由关键词/正则判断；
- objective 先驱动授权 hybrid 检索并冻结最多 24 个 chunk；
- 领域阶段通过共享 4-worker 池并行执行四个确定性 specialist，固定顺序合并并升级显式冲突；
- PRD 仍按目标排序后的前 8 个 chunk 投影需求；
- 该路径没有 Main LLM Agent、专家 Prompt 或生成模型调用。

因此仍不能回答“我在个人项目里复刻了实习中的多 LLM Agent 编排”。准确说法是：迁移了阶段划分、人机确认和治理方法，独立实现了 objective-aware 证据快照、有界领域执行、冲突升级与业务 checkpoint；问答路径另有 Agentic RAG，其 Router、Planner 和 Tool Agent 已支持受 provider 约束的结构化 JSON（OpenAI strict JSON Schema、DeepSeek JSON Object），但交付 specialist 目前不是模型角色。结构化输出也不等于模型质量，provider 拒绝、网络错误或解析失败仍回退规则路径。

### 2. “从 checkpoint 恢复”目前是业务恢复，不是执行恢复

`POST /analysis/sessions/{id}/confirm` 会读取持久化会话与创建时冻结的证据快照，校验 token，然后调用 `resume_six_stage_analysis(...)`。它原样保留阶段 1–4，只重算收敛和 PRD；响应暴露检查点版本、证据 revision 与 hash，页面刷新后可以重新 GET 验证。

它不同于简历里的 Codex AppServer + WebSocket：当前没有常驻执行上下文、节点级 continuation、实时流重连或服务端推送。前端使用 HTTP，媒体任务使用轮询。

同一 `resume_token` 最终通过 `session + tenant + owner + status + token` 条件更新原子消费。并发回归用两个请求竞争同一 token，结果为一个 200、一个 409。边界仍然是：当前不能从某次模型调用或 Python 栈的中间位置继续，也没有服务端实时推送。

### 3. “Skill/Knowledge 自进化”只实现了治理后的子集

项目真正实现了两条不同链路：

- 业务 Knowledge：PRD 发布产生候选，人工再次批准后原子物化 document/chunk/graph/provenance，并进入未来 RAG；
- 工程 Skill：仓库知识生成语义路由索引，复用未变化向量，用 corpus revision 让查询缓存失效。

当前没有自动从线上 Bad Case 诊断根因并生成/合并 Skill 规则，也没有对照 Wiki 自动生成变更并发布。批准知识已经实现申请、重新审批、supersede/revoke、缓存 revision、图谱失效和历史引用状态，但仍是人工门禁的业务知识演进。因此可以说“实现了受治理的知识演进”，不能说“完整复刻了自动自进化”。

### 4. 98% 不是通用模型准确率

V6 黄金集是 42 个手工问题、4 份固定文档，其中 37 个应回答、5 个应拒绝。评测关闭 LLM Router，使用确定性路径，以预期文档和事实子串判断结果。

当前 98% decision 是 41/42 四舍五入，97% recall@3 和 fact 是 36/37 四舍五入。它能证明固定语料上的检索/拒答回归没有退化，但不能证明开放域模型质量、真实客户分布或六阶段 PRD 质量。

### 5. 测试数量不能替代生产事实

176、135 和 33/33 是可信的工程证据，但面试官会继续问：

- 数据量和并发量是多少？
- MySQL、Redis、RocketMQ、对象存储和真实模型是否在统一链路跑过？
- P95、错误预算、容量、数据保留、撤权和灾备是否经过业务批准？
- 是否有真实用户、采用率、节省工时或 PRD 人工修改率？

当前答案分别是“只有局部/历史子系统证据”“统一 localhost 主线使用 light/mock”“生产决策未批准”“没有真实 ROI 数据”。主动说明会显得成熟，回避或编数字会反噬整个项目。

## 四、资深面试官连续追问模拟

以下不是题库背诵，而是面试官会沿着一个回答继续向下打穿的追问链。

### 第一轮：先判断是不是“两个 Demo 硬拼”

**面试官：** 用一句话说清用户是谁、什么时候用、最终得到什么。

继续追问：

1. 产品经理为什么不用飞书妙记加 ChatGPT？
2. “可回放证据”之外，你提供了什么不可替代价值？
3. Media 和 Agent 为什么需要两个数据库、两个服务？
4. 如果只有你一个人维护，分布式复杂度值得吗？
5. 有真实用户和 ROI 吗？没有的话，需求是怎么验证的？

优秀回答要点：把差异落在授权证据、审批、不可变版本、知识治理和行动副作用；承认需求来自可验证场景假设，下一步用 PRD 周期、证据回查率、人工修改率和行动关闭率验证，不编造用户数据。

危险回答：“因为用了 RAG、多 Agent、微服务，所以比现成工具更企业级。”这只是在复述技术名词。

### 第二轮：打开六阶段代码，质疑 Agent 真实性

**面试官：** 你说六阶段 Agent，为什么 `analysis_pipeline.py` 看起来只是正则、切片和字符串拼接？

继续追问：

1. 模型调用在哪里？Prompt 在哪里？
2. 四个 specialist 并行在哪里，为什么仍不叫多 LLM Agent？
3. 领域冲突怎么检测和合并？
4. objective 如何参与检索，为什么要冻结 Top-24？
5. 为什么前 8 个 chunk 可以直接等于 8 条需求？
6. 这段代码和普通 workflow 有什么区别，为什么叫 Agent？

优秀回答要点：承认六阶段交付路径仍是确定性 baseline，不是完整多 LLM Agent；指出 objective-aware hybrid、canonical snapshot、共享 4-worker、固定合并、失败隔离、冲突问题和 PRD V1 门禁的具体代码。解释为何 Phase 1 选择无外部模型可复现，并把模型专家收益留给真实数据 A/B，而不是先加 Prompt。

危险回答：“规则只是 fallback，实际都是大模型。”当前代码不支持这个说法。

### 第三轮：拿简历和代码对质

**面试官：** 简历里的 PD-Agent 也是完全相同的六阶段。你是不是把公司方案或代码搬到了个人项目？

继续追问：

1. 哪些设计来自实习，哪些由你在个人项目里重新决定？
2. 为什么没有领域 Agent、钉钉专家、AppServer 和 WebSocket？
3. 公司系统的状态文件与这里的 SQLite session 有什么不同？
4. 你能否展示公司 Prompt、数据或接口？
5. 这个项目能证明你的哪项能力，而不是证明公司方案有效？

优秀回答要点：公司代码与数据完全不进入仓库；迁移的是六阶段、人机边界、知识治理方法。个人项目重新实现了跨服务身份、证据、审批、物化和验收；明确列出四个没有复刻的能力，并拒绝披露内部细节。

危险回答：“整体架构差不多，只是换了技术栈。”这会同时触发知识产权和个人贡献质疑。

### 第四轮：打穿等待恢复语义

**面试官：** 你说从 checkpoint 恢复，究竟保存了什么，哪些阶段还会重跑？

继续追问：

1. 哪些数据真正持久化了？
2. 进程在模型调用一半时崩溃能从节点继续吗？
3. 页面刷新为什么能看到历史，是 WebSocket 重连还是重新 GET？
4. 同一个 resume token 并发提交两次会怎样？
5. token 是否真正一次性消费？
6. 如果人工确认等待 7 天，旧证据发生变化怎么办？

优秀回答要点：当前是业务阶段恢复，不是执行栈恢复；SQLite 保存 session/stages/questions/answers/PRD 与冻结 evidence snapshot/hash/revision。确认保留阶段 1–4，只重算 convergence/PRD，并用 `UPDATE ... WHERE status='WAITING_CONFIRMATION' AND resume_token=?` CAS 推进版本。两个竞争请求一个 200、一个 409；等待 7 天期间新证据不会进入旧 session，若要纳入必须新建分析或未来显式 rebase。

危险回答：“token 是一次性的，所以不会并发。”API 比较 token 不等于数据库原子消费。

### 第五轮：追问 Knowledge 自进化是否只是改状态

**面试官：** PRD 批准后再点一次按钮，为什么这叫知识演进？

继续追问：

1. 为什么 PRD 发布和知识批准要分开？
2. 如何证明知识真的进入未来 RAG？
3. 错误知识如何撤回？撤回后缓存、图谱和历史回答怎么办？
4. 同一事实更新时是覆盖、追加还是 supersede？
5. team 为什么不能由提交者自己批准？
6. Skill 自进化和业务 Knowledge 是不是同一套向量？
7. Bad Case 会自动修改规则吗？

优秀回答要点：解释候选/版本/hash/evidence/provenance、原子物化和未来召回；替代生成新 document/version 并软失效旧版，撤回只影响未来检索，content revision 使 Chunk 缓存失效，图谱在同一事务按 scope 重建；旧聊天保存来源快照并在回放时刷新当前状态。说明两套索引完全隔离，并承认升级前旧日志无法补齐来源、Skill 规则仍需人工证据与门禁。

危险回答：“系统会自动学习并越来越聪明。”当前实现的核心恰恰是禁止无审批自动污染知识。

### 第六轮：质疑 RAG 评测数字

**面试官：** 98% 是怎么算的？样本多少？为什么可信？

继续追问：

1. 是 98/100 吗？
2. 训练集和测试集是否隔离？
3. 是否开启真实 LLM？
4. fact coverage 为什么用“任一事实子串”就算通过？
5. 4 份文档、42 个问题能代表客户访谈吗？
6. 六阶段 PRD 的完整性、冲突识别、引用正确性在哪里评测？
7. 如何防止你针对黄金集调规则？

优秀回答要点：准确说 RAG 是 42 个闭集案例、41/42 decision、36/37 recall/fact；PRD 是另一个 12 例闭集，当前十项质量指标 100%、本机验证 P95 约 17～25 ms。两者都关闭 LLM，只作为确定性回归门禁。承认 PRD 集与规则共同维护、没有 holdout/真实分布，下一步需要匿名真实坏案例、独立评审和人工修改率。

危险回答：“模型准确率 98%，所以效果很好。”这是最容易被当场判定夸大的说法。

### 第七轮：追问跨服务一致性

**面试官：** Media 已完成转写，但 Agent 永远收不到，系统是什么状态？

继续追问：

1. 为什么业务事务和消息不能直接一起提交？
2. outbox 是谁扫描、如何退避、什么时候 DEAD？
3. Agent 收到重复 event 怎么处理？
4. 同一 transcript version 内容不同为什么不能覆盖？
5. 事件有顺序保证吗？
6. 为什么跨服务投递不用 RocketMQ？
7. outbox 表无限增长怎么办？

优秀回答要点：at-least-once、event ID + semantic version 双幂等、冲突保留旧事实、可重放和 DEAD 运维；明确当前跨服务 outbox 通过 HTTP 投递。顺序、归档和多实例 dispatcher 竞争是生产化需继续回答的问题。

危险回答：“RocketMQ 保证 exactly-once。”项目没有这个实现，RocketMQ 也不能自动给出业务 exactly-once。

### 第八轮：追问授权、缓存和撤权

**面试官：** 一个用户从 team 被移除，但 JWT 还没过期，他还能读数据吗？

继续追问：

1. 为什么切换 Workspace 必须重签 JWT？
2. personal 和 team 的 owner 语义为什么不同？
3. 跨租户为什么返回 404 而不是 403？
4. 检索为什么必须先授权再排序？
5. Chunk cache 为什么包含 DB path 和 revision？
6. 角色变化如何让缓存立即失效？
7. 播放 token 和 Agent JWT 的信任边界是什么？

优秀回答要点：当前角色变化在下一次重签后生效，短期 JWT 仍存在撤权窗口；这是正式 IdP/即时撤权待决策。解释 tenant/owner scope、404 防枚举、授权下推和 scope-aware cache，而不是声称已经解决即时撤权。

危险回答：“缓存里不存 JWT，所以不会越权。”缓存内容是否越权取决于查询和 key 的授权范围，不取决于是否保存 token。

### 第九轮：追问生产化和容量

**面试官：** 明天给 100 个团队、10 万小时视频，你敢上线吗？

继续追问：

1. 媒体 worker、转写配额和数据库哪个先爆？
2. SQLite 检索什么时候迁向量数据库？
3. 为什么没有版本化数据库迁移？
4. 监控为什么只是进程级指标？
5. 备份恢复演练过 RTO/RPO 吗？
6. 数据和模型供应商保留策略是什么？
7. WebSocket、SSE、轮询怎么选？

优秀回答要点：明确“不敢直接上线”，先确定身份/保留/模型策略，再用代表性负载测试媒体 worker、队列 oldest age、连接池、chunk 扫描和模型延迟。根据预算触发关系库、向量库、指标聚合和传输层升级。

危险回答：“架构已经支持横向扩展，只需要加机器。”当前数据库、缓存和调度语义没有证明这件事。

### 第十轮：追问个人贡献和 AI 辅助

**面试官：** 这个仓库由多个模型迭代过，你到底做了什么？

继续追问：

1. 哪些模块来自原 Video Platform、哪些来自原 Agent 项目？
2. 哪三个架构决定是你做的，替代方案是什么？
3. 随机打开一个核心文件，你能否解释每个状态转换？
4. 哪个 Bug 是你通过真实联调发现而不是模型告诉你的？
5. 如果移除 AI 工具，你是否能独立定位问题、写测试和评审生成代码？

优秀回答要点：如实区分迁移来源、整合、新增模块和 AI 辅助；把个人价值放在需求边界、决策、验证和对结果负责。并发迁移竞态是较好的真实故障故事，但要能解释根因、修复和生产替代方案。

危险回答：“所有代码都是我独立手写”或“模型帮我写，但最终能跑”。面试官关心的是是否真正拥有设计与代码理解。

## 六、回答任何追问都使用这套结构

1. **结论**：先回答是或不是，不用架构名词绕开问题。
2. **代码**：指出实际模块、状态或数据键。
3. **证据**：说明测试、负向用例、浏览器联调或评测分母。
4. **取舍**：为什么当前选择适合本地工程型试点。
5. **边界**：没有实现什么，什么指标或业务条件会触发升级。

示例：

> 目前不是执行栈级 checkpoint，而是业务阶段级恢复。代码把 session、阶段结果、待确认问题、答案与冻结 evidence revision/hash 存在 SQLite；确认时保留阶段 1–4，只重算收敛和 PRD，并用数据库 CAS 一次性消费 token。33 项纵向验收和双请求回归证明链路可恢复且旧 token 被拒绝，但不证明长时模型任务能从节点中间续跑。

## 七、面试官最终可能给出的三种评价

### 讲得好

> 候选人没有把 Agent 等同于 Prompt，能把模型输出和确定性副作用分开；跨服务身份、证据、审批、幂等和知识治理做得完整。对规则基线、闭集评测和生产缺口也足够诚实，具备把 AI 功能做成工程产品的潜力。

### 讲得一般

> 项目内容很多，但回答主要是 RAG、微服务、向量、缓存等名词。能演示 happy path，却说不清六阶段代码为何没有模型、98% 的分母以及恢复语义。更像包装完整的作品集，个人技术判断仍需验证。

### 讲崩了

> 声称复刻公司 PD-Agent、AppServer/WebSocket、多 Agent 并行和自动自进化，但仓库代码无法支持；把 localhost mock、42 例闭集和测试数量包装成生产效果。项目实现有价值，但候选人的可信度不足。

## 八、当前最值得补的缺口

如果只为近期面试，优先级不是继续堆功能，而是：

1. **面试必做，已完成**：统一使用“业务阶段级恢复”“有界确定性 specialist”“人工门禁后的知识演进”，并能现场指到 objective snapshot、CAS 和 PRD eval。
2. **下一批真实反馈驱动**：收集匿名坏案例和 PRD 人工修改记录，把 12 例开发集外再冻结 holdout，并由第二人独立标注。
3. **P1 知识生命周期，已完成**：approved knowledge 的 supersede/revoke、缓存/图谱失效、历史引用状态和审计化回滚已经实现并进入独立黄金门禁。
4. **P1 模型化实验**：只有真实坏案例证明规则上限后，再给 specialist 增加 schema-constrained LLM 实现，与当前基线做质量/延迟/成本 A/B。
5. **P2 生产证据**：真实试点或岗位明确要求时，再做 IdP、正式迁移、统一中间件故障注入、容量和告警。

当前可以正式收尾并用于面试：并发正确性、目标检索、冻结证据、阶段恢复、领域并行、知识生命周期和三套 Agent 门禁都有代码证据。剩余主要风险不再是“仓库里缺一段好看的 Agent 代码”，而是真实数据代表性、生产运行证据和大规模图谱增量失效能力。
