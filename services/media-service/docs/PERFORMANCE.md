# 性能与参数说明（PERFORMANCE）

> 原则：每个参数都给出依据，每个数据都可复现。本机数据环境：Windows 10 / Temurin JDK 18 / H2 内存库 / Mock 转写，复现方法见各节。

## 二、核心参数与依据

### 1. 本地线程池：core=2 / max=4 / queue=50（AsyncConfig）

**54/80 的精确解释**：JDK `ThreadPoolExecutor` 的扩容顺序是 core → 队列 → max。80 个任务并发到达时：4 个进入线程(2 core + 队列满后扩到 2) + 50 个排队 = **恰好 54 个被接收，26 个被拒绝**——异步实验室的实测数字不是随机结果，是这三个参数的直接函数。拒绝的任务已落库，由 stale-task reaper 10 秒后重投递，最终 80/80 完成。

**为什么 max 故意只有 4**：worker 执行的是 FFmpeg + Whisper + LLM 三个外部 I/O，线程数再大只是在 API 侧排队，还会放大对外部 API 的并发压力与费用。瓶颈应在 worker 数与外部配额联动调整，而不是线程池本身。

### 2. RocketMQ consumer-threads=4：对齐原则

MQ 开关 A/B 时，consumer 线程必须与本地线程池 max=4 对齐，否则「MQ 更快」的结论会被「更多 worker」污染。历史上曾用默认 20 消费线程得出错误结论，修正过程记录在 RESULTS.md——这是压测方法论的好例子。

### 3. BCrypt strength=10（默认）：登录预算分解

| 登录请求耗时构成 | 实测 |
| --- | --- |
| BCrypt matches (strength=10) | ~88 ms |
| H2 查询 + JWT 签发 + HTTP 开销 | ~24 ms |
| **合计 p50** | **111.8 ms** |

strength 每加 2 耗时 ×4（实测 12→340ms、14→1446ms）。登录不是高频接口，strength=10 是「单次验证 <100ms」与「离线爆破成本」的平衡点；若迁到登录 QPS 更高的场景，应换 WebAuthn/验证码前置，而不是降 strength。

### 4. 登录限流 5 次 / 300 秒：撞库速率上限推导

- 无限流时：BCrypt 88ms/次 → 单线程在线撞库 ~11 次/s ≈ 4 万次/h；
- 加限流后：同用户名窗口内最多 5 次 → **60 次/h**，10 位密码空间下在线爆破在数学上不可行；
- 命中限流后不做密码比对——避免攻击者用响应时间探测「被限流的用户名是否存在」；
- 限流器本身 0.29µs/op，相对 BCrypt 可忽略，不需要为它做任何优化。
- 单价说明：按用户名限流防不了分布式换 IP 撞库，生产应升级为「用户名 + IP」双维度（代码已按接口抽象，替换实现即可）。

### 5. JWT 有效期 86400s + 登出黑名单 TTL

24h 有效期是「无 refresh token 基础设施下的用户体验折中」：短有效期意味着用户频繁重新登录。登出黑名单（jti + TTL=剩余寿命）保证「主动登出立即失效」，条目体积上界 = 登出次数 × 令牌剩余寿命，自动过期无需清理任务。若要缩短有效期，应先补 refresh token 机制，否则直接改小只会伤害体验。

### 6. stale-task-timeout=60m：补偿的误伤边界

补偿 reaper 会把停留在 QUEUED/TRANSCRIBING/SUMMARIZING 超过 60 分钟的任务重置重投。指标直方图给 e2e 的上界是 600s（重度积压场景），60 分钟 = **6 倍安全余量**——再长的真实处理（如 4K 长视频）应显式调大该值，否则会出现「正在处理被误判为卡死」的重复处理。这个参数必须与任务真实时长分布联动，不是拍脑袋常量。

### 7. quota=5 任务/用户：外部 AI 成本护栏

每次任务的真实边际成本 ≈ Whisper 转写（按时长计费） + LLM 摘要（按 token 计费）+ 存储。以 1 小时视频、转写单价 P_w 元/小时、摘要 5k token、LLM 单价 P_l 元/M token 估算：

```
单任务成本 ≈ P_w + 5×P_l/1000（以各官网当日价格为准）
```

quota=5 限制的是**并发在途任务数**（QUEUED/TRANSCRIBING/SUMMARIZING），单个用户最多同时占用 5 倍单位成本的在途预算；恶意用户无法把队列和 API 配额刷满。免费/试用产品的标配防线。

### 8. 分片上传：chunk=2MB × 并发 4（前端）

2MB 的依据：移动网络平均 RTT 50-100ms、有效带宽 5-20Mbps 时，2MB 分片的单块传输时间落在 1-3s，失败重传成本可控；更小（如 256KB）会让请求数和 Redis 会话记录暴涨，更大（如 16MB）则一次抖动就要重传大量数据。并发 4 与浏览器同域 HTTP/1.1 连接数上限对齐，避免挤占 API 请求。

### 9. Redis Lettuce pool max-active=8

应用对 Redis 的使用集中在分片会话读写与锁，均为短命令；8 个连接配合 4 worker 已绰绰有余。无界连接池在 Redis 抖动时会放大为连接风暴，有界小池 + 超时（timeout 5s）才是正确姿势。

### 10. 数据库索引与选择性

| 索引 | 支撑查询 | 设计依据 |
| --- | --- | --- |
| `(owner, createdAt)` | 我的视频列表 | owner 等值（高基数）+ createdAt 排序，最左前缀直接消掉 filesort |
| `(status, updatedAt)` | reaper 补偿扫描 | status IN(...) 过滤后按 updatedAt 范围淘汰 |
| `(contentMd5)` | 去重/单飞 fan-out | 精确等值命中 |

反例提醒：不要给每列单独建索引——MySQL 一条查询通常只用一个索引，多余的索引只拖慢写入。

## 三、业务落地场景与容量推算

**场景 A：企业培训平台（1-5 万员工）**
痛点：内部讲师视频 500MB-2GB，办公网不稳定，同一课程全分公司重复上传。方案映射：分片+断点续传（弱网可靠） / 内容 MD5 秒传（同课程只处理一次，fan-out 复用结果） / 摘要生成课程要点。容量：假设日均 200 个新视频、平均 30 分钟，4 worker × Whisper 实测吞吐（30 分钟视频约 2-4 分钟处理）≈ 60-120 视频/h，单实例足够；成本敏感点在 API 费用 → quota + 秒传是成本护栏。

**场景 B：在线教育作业批改**
痛点：学生提交视频作业集中在截止前 1 小时（流量尖峰 20-50×均值）。方案映射：MQ 削峰把 HTTP 失败转为可恢复排队（k6 实测 10.25%→100% 成功率）+ 配额防单用户刷满 + reaper 兜底崩溃任务。

**场景 C：UGC 短视频社区（MVP 阶段）**
痛点：公网流量不可控、存储成本。方案映射：MinIO 直传降低应用服务器带宽（视频字节不过应用）+ 预签名播放 URL + 每用户 quota。此阶段不需要引入更多组件——先让单实例 + 全链路指标跑起来，用数据决定下一步。

## 四、指标口径与告警阈值（Prometheus）

| 指标 | 含义 | 建议告警 |
| --- | --- | --- |
| `video_task_e2e_seconds` p95 | 上传到终端全链路 | > 15min 持续 10min（积压/外部 API 降速） |
| `video_task_processing_seconds` p95 | 单任务处理耗时 | > 2× 基线（Whisper/LLM 变慢） |
| `video_task_skipped_total{reason}` | 去重/幂等/毒消息跳过 | `mq_poison_message` 增长 ≠ 0（消息生产侧 bug） |
| `http_server_requests_seconds` 上传接口 p95 | 接收侧健康度 | > 500ms（线程池/存储瓶颈） |
| 429 比例（登录） | 撞库/限流触发率 | 突增 10× 基线（爆破进行中） |
| 非 QUEUED 状态任务数 | 积压深度代理 | 持续增长（消费能力不足，加 worker） |

直方图上界已按业务调整：e2e 给到 600s（覆盖重度积压），否则 p99 会被 30s 默认上界钳平——这是 Micrometer 默认值最容易踩的坑。
