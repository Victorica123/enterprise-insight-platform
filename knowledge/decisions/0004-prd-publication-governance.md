# ADR-0004：PRD 发布采用个人二次确认与团队四眼审批

- 状态：已接受
- 日期：2026-08-29

## 背景

证据化 PRD 草稿需要从“可评审产物”进入正式发布态。所有场景强制不同人员审批会让只有一个 OWNER 的个人 Workspace 永远无法完成发布；允许所有 Workspace 自批又会破坏团队场景的职责分离。

该选择延续项目来源经历中的可评审 PRD、可等待确认、权限分级、合规判断收口和全链路状态恢复方法，但不宣称简历中存在逐字相同的审批规则。

## 决策

- 发布状态机为 `DRAFT_READY → PUBLISH_PENDING → PUBLISHED`，不允许 Agent 从草稿直接跳到发布。
- 个人 Workspace 使用 `OWNER_RECONFIRMATION`：OWNER 先申请发布，再通过独立请求携带一次性 token 和明确的 `PUBLISH` 确认完成发布。
- team Workspace 使用 `FOUR_EYES`：提交者不能批准自己的 PRD，必须由同 tenant 的另一位写角色成员完成。
- Workspace 类型来自受信 JWT V2 的 `workspace_type`；缺少该声明的 V1 令牌按 team 处理，禁止失败时放宽成个人自批。
- 发布状态比较更新与审计事件在同一数据库事务提交；批准后清空一次性 token。
- team 待审批队列只返回同 tenant、非当前用户提交且处于待审批状态的 PRD；跨租户操作返回 404。

## 结果

个人用户保持可完成的本地闭环，团队协作具备职责分离。两条路径共享一个状态机和审计模型，不需要复制两套发布逻辑。未来增加邀请、驳回、撤回和正式版本快照时，必须沿用现有 tenant 边界和不可静默发布原则。
